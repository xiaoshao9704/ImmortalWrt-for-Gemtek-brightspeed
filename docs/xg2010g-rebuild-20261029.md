# XG2010G rebuild after the October 28 upgrade

## PPP: retain the stable security release

Use the published **ppp 2.5.4** tarball, with package release **3**. Its
SHA-256 remains `379a630a40d858a1347f6592d671791dde12101697a743ef9900012f3765be31`.
Do not change the package source to an unreleased upstream branch.

Backport the five runtime-file changes from
[upstream PR #638](https://github.com/ppp-project/ppp/pull/638), merged as
`13ba8a58e9bfd4fe961a5043c6bb5ae9843d5bb7`:

- Clear the script child's `pppdb` pointer after closing TDB. Otherwise the
  subsequent `PPP_SCRIPT_INSTANCE` environment update can use the freed
  database and prevent ip-up/ip-down hooks from executing. The parent database
  must remain usable. This firmware enables multilink/TDB.
- Correct auth-down, the IPCP reopening ip-up path, and IPv6 up hook instance
  names.
- Correct the EAP-TLS debug formatting arguments. EAP-TLS is disabled in this
  firmware, but the complete small upstream runtime fix is retained.

Keeping 2.5.4 retains its security fixes, including
[the LCP NAK overflow](https://github.com/ppp-project/ppp/security/advisories/GHSA-frhv-j822-2pvx)
and [the PEAP overflow](https://github.com/ppp-project/ppp/security/advisories/GHSA-rwr9-4vx8-vc35),
plus script, privilege, secrets-file and input-validation hardening documented
in the [release README](https://github.com/ppp-project/ppp/blob/v2.5.4/README).
The package disables PEAP/EAP-TLS and installs pppd without setuid, so not all
advisories apply to this build. LCP remains part of PPPoE; the cited LCP issue
requires a non-default authentication configuration and must not be described
as affecting every default PPPoE connection.

## Default package and runtime repository changes

- Remove pbr, luci-app-pbr and its Chinese translation from both `2010.config`
  and `2010-2g.config`. The existing config/manifest guard now rejects their
  inclusion in XG2010G images. No live router settings are changed, and this
  does not prevent a user from installing pbr later.
- Merge [upstream PR #66](https://github.com/naoki66/ImmortalWrt-for-Gemtek-brightspeed/pull/66)
  from `cursor/omit-build-only-distfeeds-1702` at
  `2ec49f8fe49c25388df6ce1581363ec55d3de75b` into this fork. Retain the current
  pinned build feeds when resolving the feeds.conf.default comment conflict.
  Runtime APK/OPKG feeds include only published standard feeds; target/base
  and buildbot kernel repositories retain their existing handling. Build-only
  feeds still participate in compilation. Custom runtime feeds can be added
  through customfeeds.conf.
- Bump firewall4 package release 5 to 6 so the existing nft failure propagation
  patch is distinguishable from the prior package. No further firewall runtime
  behavior changes are made here.

## Validation and limits

Locally completed:

- Verified the 2.5.4 release archive hash; applied the entire package patch
  stack successfully, including the new #638 backport.
- Five host regression cases in `tests/test_ppp_script_child.py` passed. The
  harness compiles the actual prepared-source fork, environment and exec
  functions, with a guarded TDB stub and real child processes/hook execution.
  It covers strict/path execution, a null database, a build without TDB, and a
  negative control that restores the dangling pointer and fails before exec.
- `bash scripts/check-distfeeds.sh` passed.
- Both XG2010G config isolation checks passed; the prior manifest is rejected
  for containing pbr and passes after removing only its three pbr packages.
- Existing ONU bridge load-state regression suite: 27 tests passed.

To reproduce the PPP host regression after applying the package patches:

```sh
python3 tests/test_ppp_script_child.py --source /path/to/prepared/ppp-2.5.4 -v
```

These are source/host tests, not a target firmware build or PPPoE integration
test. This host has no `/dev/ppp`, so no upstream link integration result is
claimed. CI must build `2010.config`, and its resulting manifest must show
ppp 2.5.4-r3, firewall4 release 6, and no pbr packages. Physical XG2010G PPPoE
and hook execution still need validation after an explicitly authorized
installation. No live router flashing is performed as part of this change.
